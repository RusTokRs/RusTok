# RS256-only JWT architecture

- Date: 2026-11-25
- Decision status: Accepted
- Implementation status: In progress
- Owners: Auth; server host composition
- Supersedes: [Canonical JWT algorithm metadata](2026-11-25-jwt-canonical-algorithm-metadata.md) for algorithm selection and migration.
- Extends: [Mandatory JWT key identity](2026-11-25-jwt-mandatory-key-identity.md), [canonical keyring document](2026-11-25-jwt-canonical-keyring-document.md).

## Decision

Use RS256 exclusively for all repository-owned access (direct and OAuth),
password-reset, email-verification and invite JWTs. Four distinct purpose
rings retain separate active RSA pairs and bounded public-only verification
history. Require exact kid, purpose and RS256 JOSE header; no algorithm
negotiation, shared symmetric JWT signing secret, fallback, mixed history
or runtime algorithm migration. RSA modulus identity, exact public
modulus/exponent identity, key-pair validation, terminal tombstones,
emergency revocation, generation ordering, leases and authenticated
independent authority/witness remain mandatory. Normal RSA key rotation
is not legacy. HMAC-SHA256, HKDF-SHA256 and Argon2id remain in their existing
non-JWT roles. The independent MAC root must not derive JWT signing keys.
JWKS and verifier-only capability are follow-up work, not current
authorization or revocation guarantees.

## Implementation sequence

1. Remove mixed verifier admission and managed cross-algorithm promotion.
   Reject mixed persisted current snapshots and replica grants, rather than
   mutating authenticated state. Keep the existing homogeneous deployments
   operational while preparing the coordinated source cutover.
2. Inventory all AuthConfig constructors, host settings, keyring files,
   CLI/installer paths, CI, tests, examples and deployment tooling. Provision
   four independent RSA pairs explicitly; use fresh isolated test/dev
   fixtures, never production fallbacks or shipped private keys. Separate
   policy construction from file candidate validation so a configured file
   does not require a second unused key source. Replace all consumers
   atomically; reject old algorithm and HS256 fields, remove JWT algorithm
   enum, HMAC key derivation, secret inventory and mixed crypto branches.
3. Canonicalize RSA-only persisted metadata without compatibility readers.
   Preserve durable identity domains for RSA keys and all security history.
   For non-disposable state, require an explicitly authorized authenticated
   offline conversion preserving every old tombstone, revoked identity,
   generation and witness revision and preventing old HS256 tokens from
   being accepted. No retained-state converter or deployment authorization
   is delivered by this decision. Never reset authority/witness to bypass
   admission; block deployment until the conversion is available.
4. Verify source, real host bootstrap, four independent rings, negative JOSE
   admission, RSA staging/promotion/retirement, restart, replica drain,
   emergency revocation, witness recovery, installer/CLI and all affected
   deployment fixtures. No old/new dual-format reader or transitional runtime
   algorithm switch is permitted.

## Current status

Step 1 is source-implemented. The mandatory executable bootstrap slice from
step 2 is source-implemented: the server requires `RUSTOK_JWT_KEYRING_FILE`,
accepts only a complete generation-bearing document with four RS256 purpose
rings, and always performs durable generation admission before publisher
creation. The static/default generation-zero runtime path has been removed;
generation zero remains only the empty ledger state.

The Auth-owned database-free `validate-jwt-keyring` command shares the exact
document preparation and cryptographic validation path with the host. The
full development Compose migration container runs it before application
migrations. The CI reference-artifact and Rust-host browser-smoke jobs
provision one isolated four-pair RSA keyring in runner temporary storage,
pass only its path to the host and remove the private directory afterward.
The private keys are not committed, logged, cached or uploaded.

Production policy now treats `auth.jwt.secret` solely as an independent MAC
root; it is not inspected as a JWT signing key. CLI authority/witness/revocation
commands remain independent of signing private keys. The server executable
has completed the mandatory file-only consumer cutover, but the full workspace
inventory is not yet confirmed from a local checkout. Legacy generic Auth
constructors, `JwtAlgorithm`, HS256 derivation, historical algorithm
serialization, old startup-source tests and installer/test consumers still
need coordinated removal.

The canonical keyring document still carries an explicit RS256 marker in this
intermediate schema. Its removal is part of the final RS256-only document
canonicalization. Durable authenticated metadata is deliberately unchanged:
the offline authenticated converter is not implemented. Existing non-disposable
stores with incompatible HS256 state remain blocked; no authority/witness reset
or database deletion is permitted.

The independent MAC root validation rejects PEM material and weak roots at
JWT preparation, host proof and durable fence MAC boundaries. Explicit isolated
POSIX dev/test provisioning of four RSA pairs is available and never runs at
host startup. Shared test fixtures generate independent pairs per isolated
store; key identities remain stable across each store's generations. The
source regressions remain unexecuted. Follow-up review corrected mandatory-kid
and keyed-snapshot identity assertions and hardened atomic keyring publication.

The complete RS256-only cutover is pending. Stop older writers before
deploying the changed admission contract. Existing mixed persisted state is
blocked; do not delete it.
