## Covered scenario

The owner source exposes one tenant with a contiguous revision page `1, 2, 3`.
Search already has terminal inbox coverage for revisions 1 and 3, but the exact
owner event UUID for revision 2 is absent. The Search projection starts with one
stale Forum document.

The first owner sweep injects a projection-source failure during the required
current-state rebuild. The proof requires:

1. the bounded owner tenant scan discovers exactly the configured tenant;
2. the contiguous owner revision page is accepted from checkpoint zero;
3. revision 2 is classified as missing while revisions 1 and 3 are covered;
4. the rebuild failure leaves the stale Search document unchanged;
5. no checkpoint row and no checkpoint-audit row are written.

The next sweep uses the same owner state and permits the rebuild to succeed. It
must remove stale Forum projection state, insert one current owner document and
perform exactly one successful current-state rebuild for the entire revision
page.

## Exact checkpoint ordering

Search migrations already install a PostgreSQL trigger that requires the first
checkpoint to be revision 1 and every update to advance by exactly `+1`. The
proof adds an isolated AFTER trigger that records every committed checkpoint
mutation together with the number of Forum documents visible at that moment.

The retained audit must be exactly:

```text
revision 1 / rebuild_repaired / current document visible
revision 2 / rebuild_repaired / current document visible
revision 3 / rebuild_repaired / current document visible
```

This proves that no checkpoint advancement occurs before successful rebuild and
that the missing revision is not skipped. The final checkpoint must reference
the exact revision-3 owner event UUID. A third caught-up sweep must create no
additional audit row and must not call the projection source again.

Owner revisions remain a Forum-owned causal clock and are never compared
numerically with Search `ingest_sequence`.

## Runtime placement

D3-D5 external-Iggy proofs live in the `rustok-server` host package after #2781.
D6 does not require Iggy and remains in `rustok-search`, which already owns the
PostgreSQL reconciler, migrations, projection source contract and required test
dependencies. No Cargo dependency or lockfile change is introduced.

The test uses a PostgreSQL connection URL with a per-connection `search_path`
because the reconciler transaction and nested projector transaction require a
pool with more than one connection.

## Deliberate boundary

D6 does not execute the host polling loop, Iggy delivery, acknowledgement,
poison or DLQ behavior. It does not prove contention between separate server
processes, advisory-lock exclusion under concurrency, scan-cursor contention,
deletion or ACL ordering, Search-disabled recovery, storefront visibility or
`LINK-FORUM-03` completion.

Those remain separate bounded runtime slices under the parent D0 protocol.
