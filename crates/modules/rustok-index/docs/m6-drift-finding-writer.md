# M6 drift digest finding writer

Status: `source_complete_snapshot_reader_and_repair_pending`.

## Purpose

`PostgresIndexDriftFindingWriter` provides one Index-owned transactional persistence boundary for an already-computed source/index SHA-256 mismatch.

The writer consumes `IndexDriftDigestFindingRequest`. It does not scan a source, query Index entities, calculate either digest, infer an orphan, choose repair policy, or mutate indexed data. The database-neutral diagnosis producer computes expected and actual digests before calling this boundary; a production snapshot reader remains open.

## Request contract

A request requires:

- one non-nil tenant UUID;
- one non-empty, trimmed, control-character-free check name bounded to 128 UTF-8 bytes;
- one typed `Info`, `Warning`, or `Error` severity;
- one typed global, schema, locale-bearing entity, or locale-free entity scope;
- one exact 64-byte lowercase hexadecimal expected digest;
- one exact 64-byte lowercase hexadecimal actual digest;
- different expected and actual digests.

Schema scope requires a positive schema version. Both entity variants additionally require a non-nil entity UUID. A locale-bearing entity requires a canonical locale whose persisted form is at most 32 UTF-8 bytes; a locale-free entity persists `locale_key = NULL` and never invents a locale.

The request accepts no finding UUID, lifecycle state, timestamp, actor, reason, raw JSON details, SQL, database error, source payload, mutation payload, or transport context.

## Deterministic finding key

The writer derives one lowercase SHA-256 finding key from a versioned length-prefixed contract containing:

- tenant UUID;
- check name;
- exact scope kind;
- exact schema identity and version when applicable;
- exact entity UUID and locale component when applicable.

The existing locale-bearing entity sequence is unchanged. Locale-free entities use one length-prefixed NUL byte as the final component; a canonical `LocaleKey` cannot contain NUL. This preserves every existing locale-bearing finding identity while keeping locale-free identity distinct.

Expected and actual digests are deliberately excluded from the key. Repeated observations of the same tenant/check/scope therefore refresh one durable finding instead of creating an unbounded row per changing digest pair.

Tenant identity is included in the hash so externally visible finding keys do not correlate the same check/scope across tenants.

## Transaction and concurrency

`record_digest_mismatch` opens one database transaction and serializes the exact tenant/finding key with a PostgreSQL transaction advisory lock. SQLite is supported only for source tests and relies on its write transaction.

Inside the transaction the writer:

1. loads the exact `(tenant_id, finding_key)` row, using `FOR UPDATE` on PostgreSQL;
2. verifies the stored check name and persisted scope still match the deterministic key contract;
3. inserts a new open finding when no row exists;
4. otherwise applies the exact lifecycle transition described below;
5. commits only after exactly one insert or update succeeds.

The insert also uses the existing unique `(tenant_id, finding_key)` constraint with `ON CONFLICT DO NOTHING`. A conflict is reloaded and validated inside the same transaction.

Database failures map to one stable detail-free `Storage` error.

## Lifecycle semantics

The finding UUID and `first_detected_at` are generated only on first insert and remain stable afterward.

- absent row -> `Created` and `state = 'open'`;
- existing `open` row -> `Refreshed`;
- existing `resolved` row -> `Reopened`, `state = 'open'`, and `closed_at = NULL`;
- existing `ignored` row -> `Suppressed`; state and closure remain ignored while current bounded evidence and `last_detected_at` are refreshed.

Every refresh may update severity, expected digest, actual digest, and `last_detected_at`. It never changes finding UUID, finding key, check name, scope, or first-detected time.

Unexpected stored state or identity drift fails closed. Ignored findings are never automatically reopened.

## Private details contract

The required `details` column is always generated by the writer as exactly:

```json
{
  "contract": "index_drift_digest_finding_v1"
}
```

Callers cannot add arbitrary details. Tenant identity, source values, entity payloads, credentials, request data, SQL, database causes, stack text, actor identity, repair reason, and transport context are not persisted there.

## Migration and inspection

The historical M3 migration remains unchanged. `m20260804_000005_relax_index_finding_locale_scope` replaces only the finding table scope CHECK so entity rows may have `locale_key = NULL`; every other scope, digest, state, and closure invariant remains.

`PostgresIndexDriftFindingInspector` decodes locale-bearing entity rows as `Entity` and locale-free rows as `EntityWithoutLocale`. It remains read-only and tenant-scoped. The writer and inspector are not composed into a public mutation transport.
