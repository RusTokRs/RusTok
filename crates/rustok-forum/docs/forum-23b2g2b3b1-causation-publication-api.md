`source_complete_family_publisher_pending`

accepted Forum Search versioned invalidation rollout. It does not add the new
Forum Search event family, update the event registry or digest artifact, or
change the Forum publisher.

The frozen rollout remains defined by:

```text

```

## Why this is a separate slice

Adding `ForumSearchProjectionEvent` changes both the event registry digest and
the `ContractEventPayload` and `ContractEventEnvelope` JSON-schema digests. Those
values are generated by the `rustok-events` schema example and must not be
guessed or committed as placeholders.

The implementation agent was explicitly asked not to run Cargo commands or
digest generation. The safe boundary is therefore to deliver the schema-neutral
causation API first. The next slice can add the family, deliberately regenerate
the artifact, and wire Forum dual publication as one reviewed release change.

## Typed envelope API

`ContractEventEnvelope` already serialized an optional `causation_id`. This
slice adds public construction and read access without adding, removing, or
renaming any wire field:

```text
ContractEventEnvelope::new_caused_by
ContractEventEnvelope::causation_id
```

`new_caused_by` uses the same path as the existing `new` constructor:

1. validate the sealed event payload;
2. derive its registered event type and schema version;
3. create the typed envelope and correlation identity;
4. retain the supplied predecessor in envelope `causation_id`;
5. run complete registered-envelope validation.

A nil causal UUID fails as `EventValidationError::NilUuid("causation_id")`.
Tenant, actor, trace, event metadata, payload validation and schema lookup keep
their existing fail-closed behavior.

The existing `ContractEventEnvelope::new` remains source-compatible and creates
an envelope with no causal predecessor.

## Transactional outbox APIs

The composed owner path now exposes:

```text
TransactionalEventBus::publish_contract_in_tx_with_causation
TransactionalEventBus::publish_contract_in_tx_with_causation_and_envelope_id
```

The second method returns the exact new typed-envelope UUID written by the same
transaction. The first delegates to it and discards only that returned identity.
Neither method reconstructs an ID after persistence.

Some Forum write helpers receive the active database transaction but do not
receive a composed `TransactionalEventBus`. They can use:

```text
TransactionalEventBus::publish_contract_direct_in_tx_with_causation_and_envelope_id
```

Despite the `direct` name, this is not a direct broker or process-local path. It
validates a sealed contract envelope and calls the same crate-private canonical
outbox writer:

```text
OutboxTransport::write_contract_envelope_in_tx
```

The API exists only to mirror the previously delivered transaction-only root
publisher. It requires the live owner transaction and cannot publish outside
that transaction.

## Compatibility and digest boundary

This slice deliberately leaves unchanged:

- `ContractEventPayload` variants;
- the event registry and every registered event schema;
- `ContractEventEnvelope` serialized fields;
- `event-contract-digests.json`;
- root event publication;
- outbox table shape and relay behavior;
- Iggy producers or consumers;
- Forum projection invalidation publication;
- Search inbox, projector, checkpoint or worker behavior;
- dependencies and `Cargo.lock`.

Because only constructors, accessors and publication methods are added, the
committed registry and wire-schema digest values remain the current values.

## Next slice

`FORUM-23B2G2B3B2` must complete the publisher half of the rollout atomically:

1. add sealed v1 `ForumSearchProjectionEvent::InvalidationIssued`;
2. register `forum.search_projection.invalidation_issued`;

5. allocate the Forum owner revision;
6. publish the legacy root and retain its envelope ID;
7. publish the typed event with that ID as `causation_id`;
8. append the owner ledger using the legacy root ID;

adapter remain `FORUM-23B2G2B3C`.
