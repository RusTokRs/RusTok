## Why D0 is separate from runtime completion

The earlier A and B2 handoff documents still described later merged slices as
future work, and the canonical `FORUM-23` ledger stopped at `FORUM-23B2G1`.
Promoting the task directly to runtime-complete would be false because the
implementation PRs intentionally ran no PostgreSQL, Iggy, restart, poison, DLQ,
or cross-module proof.

D0 therefore performs only these bounded actions:

1. synchronize the historical A/B/C handoffs with the actual merged rollout and
   record the remaining canonical-ledger gap explicitly;
2. define exact required runtime scenarios and evidence fields;
3. add a fail-closed static verifier for handoff, protocol and source drift;
4. leave `FORUM-23` and `LINK-FORUM-03` `in_progress` until executable evidence
   is generated by the maintainer.

The canonical plan remains authoritative. Its `FORUM-23` ledger and task card
must be reconciled with the delivered B2G2 chain before runtime completion is
claimed; D0 does not silently rewrite that large unrelated backlog surface.

## Required runtime profiles

The evidence run must use:

- PostgreSQL;
- `rustok.events.delivery_profile=outbox_iggy`;
- `RUSTOK_FORUM_SEARCH_CONTRACT_CONSUMER_ENABLED=true`;
- persistent consumer group `rustok-search-forum-projection-v1` on topic
  `domain`;
- at least two server processes for the serialization case.

SQLite remains a validation-only profile for this boundary. A process-local or
in-memory consumer is not acceptable runtime evidence.

## Required scenarios

The executable evidence artifact must cover all scenarios listed by the machine
contract, including:

- normal owner transaction, typed delivery, projection and checkpoint advance;
- legacy-first and typed-first duplicate races collapsing on one root identity;
- acknowledgement failure followed by restart and exact durable duplicate
  recognition;
- raw poison and semantic inbox-identity conflict through durable connector-owned
  receipts and deterministic DLQ publication;
- missing-delivery repair discovered from the Forum owner ledger;
- multi-process advisory-lock and checkpoint serialization;
- hide, delete and richer ACL ordering without stale content restoration;
- Search-disabled owner-command continuity and later bounded reconciliation.

A scenario is not complete if it proves only source shape or a unit-level
adapter. The retained artifact must correlate owner state, root and typed event
identities, Search inbox rows, `ingest_sequence`, owner checkpoints, poison/DLQ
receipts and the final storefront visibility assertion.

## Evidence artifact policy

The runtime runner must generate:

```text
target/forum-search-versioned-invalidation-runtime-evidence.json
```

The artifact is executable output. It must not be hand-edited or replaced with a
static fixture. At minimum it records the exact source commit, database backend,
delivery profile, consumer group, per-scenario result, owner revision rows,
root/typed identities, Search inbox rows and sequences, owner checkpoints,
poison/DLQ receipts and storefront visibility assertions.

D0 does not add fabricated output at that path.

## Compatibility and degraded mode

No migration, event schema, digest, public DTO, Search query, Forum owner command,
broker topic, consumer group, inbox table, projector, reconciliation checkpoint,
dependency or `Cargo.lock` change is introduced by D0.

The persistent typed consumer remains default-off. The mandatory legacy root
publication remains active. Search-disabled deployments keep Forum owner writes
and transactional event publication independent from Search availability.

## Remaining scope
