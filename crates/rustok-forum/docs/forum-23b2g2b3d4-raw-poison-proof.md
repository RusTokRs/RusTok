## Covered scenario

The test publishes two malformed byte sequences to an isolated one-partition
external Iggy stream while using the production Forum Search consumer group
`rustok-search-forum-projection-v1` and topic `domain`.

For the first delivery it requires:

1. contract decoding fails with the stable connector classification
   `iggy.contract.decode_invalid`;
2. immutable stream/topic/partition/offset coordinates and exact bytes derive one
   RFC 9562 UUIDv8 connector delivery identity;
3. one PostgreSQL `iggy_consumer_poison_receipts` row is claimed in `publishing`;
4. the DLQ entry carries that same delivery UUID as both its transport event field
   and explicit deterministic Iggy broker message ID;
5. the exact bytes are observed once on the physical Iggy `dlq` topic;
6. the durable receipt reaches `published` before the source offset is acknowledged.

The first source cursor is then dropped without acknowledgement. Reopening the
same production consumer group must redeliver the exact offset, delivery UUID,
classification and bytes. A second `reserve_and_claim` call must return
`AlreadyPublished`, preserving the original delivery-attempt count. No second
physical DLQ message may appear.

Only after this durable terminal result is reused does the test acknowledge the
source delivery and transition the receipt to `acknowledged`. The next raw
fixture must then have a later source offset and a different connector delivery
UUID, proving the group advanced.

## Deterministic identity boundary

The connector delivery UUID is not a trusted domain event ID or tenant ID. It is
derived only from the source stream, topic, partition, offset and exact broker
bytes. `ConsumedContractDecodeFailure::to_dlq_entry` attaches it as the explicit
broker message identity, and the external Iggy DLQ publisher passes that UUID to
the Iggy message header.

The durable PostgreSQL receipt remains the exactly-once decision record. Broker
message identity provides deterministic publication identity, but does not
replace receipt-state ordering.

## Compatibility and degraded mode

This slice retains only a host-owned integration test, contracts,
documentation and a static verifier. The server package already owns direct
Search, Iggy and connector dependencies, so the proof adds no package edge and
requires no `Cargo.lock` change. It does not change production migrations,
event schemas or digests, public DTOs, Search queries, broker topology, the
default-off server consumer flag, or the mandatory legacy
`index.reindex_requested` path.

The test skips explicitly when either the PostgreSQL URL or external Iggy
address is absent. A skip does not create the evidence artifact and is not a
successful runtime claim.

## Deliberate boundary

D4 does not execute the server-owned Forum Search worker loop or its retry
backoff. It does not inject a DLQ publish failure, a durable publish-mark
ambiguity, a poison identity collision, or semantic inbox identity-conflict
poison. It does not execute the Search projector, advance an owner checkpoint,
prove multi-process serialization, validate deletion/ACL ordering, exercise the
Search-disabled profile, or close `LINK-FORUM-03`.

Those remain separate bounded runtime slices under the parent D0 protocol.
