## Process topology

The parent test creates one isolated PostgreSQL schema and then launches the
same `rustok-server` integration target as separate child processes using the
Rust test harness `--exact` filter.

The process roles are:

1. `holder` reads the initial null scan cursor, opens the first tenant, acquires
   the production tenant advisory transaction lock and pauses inside the Forum
   current-state projection source;
2. `contender` independently reads the same initial cursor and first tenant,
   fails to acquire the advisory lock, reports the tenant as blocked, and
   attempts the scan-cursor compare-and-set;
3. `next` runs after the first tenant completes and must open the second tenant
   from the retained cursor.

The holder and contender overlap in real OS process lifetime. They use separate
SeaORM pools and database sessions; they do not share a Tokio runtime, an
in-memory mutex, an owner-source object, or projection-source state.

## Tenant lock exclusion

The holder pauses only after `ForumOwnerCheckpointReconciler` has acquired the
transaction-scoped lock derived from:

```text
search:forum:<tenant_id>:forum
```

While that process remains paused, the contender must return a sweep report
with exactly one blocked owner tenant and zero rebuilds or checkpointed
revisions. Its projection source intentionally fails if called, so successful
evidence also proves that the blocked process never entered projection work.

After the parent releases the holder, exactly one first-tenant current-state
rebuild may commit.

## Scan cursor compare-and-set

Both concurrent processes loaded the same null scan cursor. The contender
finishes first and stores the first tenant UUID. The holder later attempts the
same update with its stale expected-null cursor.

The production upsert permits an update only when the stored cursor is `IS NOT
DISTINCT FROM` the expected cursor. An isolated AFTER trigger records committed
cursor mutations. Before the holder is released, the audit must already contain
one transition:

```text
null -> first tenant
```

After the holder exits, the audit must still contain exactly one row. This
proves that the stale writer neither duplicated nor regressed the cursor.

The later `next` process must add exactly:

```text
first tenant -> second tenant
```

No reset, duplicate first-tenant transition or skipped second tenant is allowed.

## Checkpoint ordering

The first tenant exposes owner revisions `1, 2`; the second exposes revision
`1`. No Search inbox delivery exists, so each successful tenant reconciliation
uses one current-state rebuild.

Search migrations already enforce that a checkpoint starts at revision 1 and
every update advances by exactly `+1`. A test-only AFTER trigger records each
committed checkpoint mutation and the visible Forum document count.

The retained audit must be exactly:

```text
first tenant:  revision 1, revision 2
second tenant: revision 1
```

Every row must use `rebuild_repaired` and observe one current Forum document.
The blocked contender must create no checkpoint row.

Owner revisions and the UUID scan cursor remain independent from Search
`ingest_sequence`.

## Runtime placement

D7 lives in the `rustok-server` host package because the proof launches
independent host integration-target processes. It needs no Iggy broker and adds
no dependency or lockfile edge. PostgreSQL connection URLs carry a
per-connection `search_path`, because each child process and nested projector
transaction can use several pooled sessions.

## Deliberate boundary

D7 does not execute the long-running host polling loop or prove restart timing.
It does not use Iggy delivery, acknowledgement, poison or DLQ behavior. It does
not validate deletion/ACL ordering, Search-disabled recovery, storefront
visibility, aggregate `FORUM-23B2G2B3D` completion, or `LINK-FORUM-03` closure.

Those remain separate bounded runtime slices under the parent D0 protocol.
